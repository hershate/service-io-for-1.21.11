# 1.21.11 / JDK 21 兼容性改动记录

本仓库 fork 自上游 `TheNextLvl-net/service-io`。上游 `main`（v3）已逐步把构建基线漂移到 **Paper API 26.x / Java 25**，
而本 fork 只服务 **1.21.11 / JDK 21**。以下是为此做的全部改动及原因。

> 排查思路：上游 `main` 把 Paper API 从 `1.21.11-R0.1-SNAPSHOT` 一路升到 `26.2.+`（起点提交 `df9722f "Support mc 26.1+"`）。
> 最后一处仍用 1.21.11 API 的提交是 **`72767d3`**，可作为"过去版本"的参考基线。

## 1. 编译目标回退到 1.21.11（提交 `7c1cab1`）

| 文件 | 改动 | 原因 |
|---|---|---|
| `build.gradle.kts` | `paper-api:26.2.+` → `1.21.11-R0.1-SNAPSHOT` | 针对 1.21.11 编译 |
| 6 个文件 10 处 | `world.key().asString()` → `world.getName()` | `World#key()`（Adventure `Key` 风格）是 26.x 才有；1.21.11 只有 `getName()`。来自上游提交 `cabc388 "Use world key instead of name"`。对 `EconomyServiceWrapper` 还修正了语义——Vault economy 本就期望世界名而非 namespaced key |

涉及文件：`plugin/.../wrapper/service/EconomyServiceWrapper.java` 及 5 个 `*TestSuite.java`。

## 2. 切到 JDK 21 编译运行（提交 `551f5a0`）

| 文件 | 改动 | 原因 |
|---|---|---|
| `build.gradle.kts` | `toolchainJvm = 25` → `21` | 用本地 JDK 21；`--release 21` 产出 Java 21 字节码，匹配 1.21.11 运行时。**不下载 JDK 25** |
| `src/main/java/module-info.java` | `requires net.kyori.adventure.api` → `requires net.kyori.adventure` | 1.21.11 的 adventure 4.26.1 中 `adventure-api` 的模块名是 `net.kyori.adventure`（`.api` 是 26.x 新版改名后的）。上游 `0e73408 "26.2"` 才引入 `.api` |

## 3. Provider 依赖降级到 Java ≤21（提交 `551f5a0`）

部分 provider 依赖的新版本是 **Java 25 字节码**，JDK 21 的 javac 无法读取（会报"找不到符号"），
且它们本就是 MC 26.x 版本、对 1.21.11 不兼容。统一降级到 1.21.x 时期的 Java ≤21 版本：

| Provider | 依赖 | 改动 | 原因 |
|---|---|---|---|
| `providers:fancy-npcs` | `de.oliver:FancyNpcs` | `2.11.0` → **`2.9.2`** | 2.10+ 的 class 字节码是 Java 25（major 69）；2.9.2 是 Java 17、1.21.x 兼容 |
| `providers:decent-holograms` | `com.github.decentsoftware-eu:decentholograms` | `2.10.1` → **`2.9.9`** | 2.10+ 带声明为 JVM 25 的 `nms-v26` 模块（变体解析在 attr=21 下失败）；2.9.9 是 `72767d3` 时用的 1.21.x 版本 |

无需改动的 provider（其依赖本就是 Java 21）：
`citizens`（citizens-main 2.0.43-SNAPSHOT）、`fancy-holograms-v2`（FancyHolograms 2.10.0，jvm=21）、
`fancy-holograms-v3`（FancyHolograms 3.0.0-SNAPSHOT.4）、`luckperms`（api 5.5）、`group-manager`（3.2）、`superperms`。

## 5. 稳定性与数据正确性修复（高负载 / 网络服务场景）

针对"长时间高负载、多用户高频使用、作为网络服务暴露"的稳定性与数据操作正确性做的修复。
均以细粒度提交记录在 `fix/stability-and-data-correctness` 分支，`gradle build -x test` 通过。

### 5.1 数据迁移（converter）过早完成 / 丢数据

| 文件 | 问题 | 修复 |
|---|---|---|
| `PermissionConverter` / `ChatConverter` / `GroupConverter` | 外层用 `thenAccept`，内层 `target.resolve*()` 返回的 `CompletableFuture` 被丢弃（fire-and-forget）。迁移经 `allOf` 汇总后会在目标端实际写入完成**之前**就报"完成"，可能留下不完整/不一致数据。 | 外层改 `thenCompose`，正确等待目标端写入。 |
| `GroupConverter.convert()` | `source.loadGroups()` 的 future 被丢弃，且 `super.convert()`（玩家入组）与"建组"并发，玩家入组可能在组尚未创建时执行。 | 先 `thenCompose` 等待全部建组完成，再执行玩家级转换。 |

### 5.2 经济数据操作正确性

| 文件 | 问题 | 修复 |
|---|---|---|
| `wrapper/service/VaultUnlockedEconomyServiceWrapper.deleteAccount(player, world)` | 忽略 `world`，直接删全局账户（`economy.deleteAccount(plugin, uuid)`），即"删某世界账户"会删除该玩家**所有世界**的账户数据（超额删除/数据丢失）。VaultUnlocked API 无世界维度的 deleteAccount。 | 改为返回 `false`（不执行删除），避免误删其它世界数据（已与维护者确认该策略）。 |
| `wrapper/service/model/WrappedAccount` / `WrappedBank` 的 `setBalance` | 用 `double` 相减算差额，累积浮点误差，且与基于 `BigDecimal` 的 `VaultUnlockedAccount` 不一致；`WrappedBank` 还缺 `canHold` 守卫。 | 改用 `BigDecimal` 算差额；`WrappedBank` 补 `canHold` 守卫。 |
| `wrapper/service/model/WrappedCurrency.toData()` | `currencyNameSingular/Plural()` 可能为 null，`Map.of(k, null)` 会 NPE，货币转换时崩溃（与 `getDisplayName*` 的空安全守卫不一致）。 | 仅在非 null 时放入 map。 |

### 5.3 并发稳定性

| 文件 | 问题 | 修复 |
|---|---|---|
| `placeholder/api/PlaceholderStore` | `provider` 字段非 `volatile`：事件处理器（主线程）写、PlaceholderAPI `resolve()`（可能异步线程）读，高频下可能读到陈旧值（null 或已注销的 provider）。 | `provider` 改为 `volatile`。 |

### 5.4 LuckPerms provider 数据操作

| 文件 | 问题 | 修复 |
|---|---|---|
| `LuckPermsGroupController.deleteGroup(name)` | `optional.map(...::deleteGroup).isPresent()` 把删除用的 `CompletableFuture<Void>` 丢弃，只要组**存在**就返回 `true`，而删除可能尚未完成或失败。 | 用 `thenCompose` 正确等待删除完成后再返回。 |
| `LuckPermsGroup.getPermissions()` | 调用 `getPermissionData()` 未传 `options()`，是同类（含本类 `checkPermission` 与用户 holder）中唯一未传世界上下文者；世界维度组会读到默认上下文权限（读错、组间转换也会拷错）。 | 传入 `options()`。 |

### 安全性核查（网络服务）

- 所有命令经 Brigadier `.requires(hasPermission)` 做权限校验（`service.command` / `service.convert` / `service.info` / `service.admin`），无未授权可达的数据操作。
- 无任何入站 socket / HTTP 服务端代码；版本检查器仅出站访问 Modrinth。
- 占位符解析有 try/catch 兜底，不会因单个解析异常影响整体。
- `ServiceConvertCommand` 用 `AtomicBoolean` 防止并发重复触发迁移。

## 6. 第二轮审查修复（三路并行 agent 审查，逐条核实后修复）

通过三个并行审查 agent 覆盖剩余子系统（wrapper 模型 / GroupManager+SuperPerms+API / 全息图+角色+测试），
每条发现都对照真实代码与第三方 API（Vault2 / DecentHolograms / Citizens / GroupManager jar）核实后再修。
`gradle build -x test` 通过。本轮额外修复：

| 文件 | 问题 | 修复 |
|---|---|---|
| `FancyCharacter.canSee` | 可见性逻辑反转：通过各项校验后仅当 NPC 是"隐形/跳过"目标才返回 true，普通 NPC 反而 false；addViewer 因此拒绝正常玩家 | 对"隐形跳过"条件取反 |
| `CitizensCharacterController.getCharacters(World)` | 未生成 NPC 的 `getEntity()` 为 null，`getEntity().getWorld()` NPE | 加 null 判断 |
| `DecentHologram` / `DecentPagedHologramLine` 带索引方法 | 仅 `checkIndex` 校验却 `addLine`（追加），索引被忽略；`setXLine` remove+add 重排后续行 | 改用 DH `insertLine(index,...)`；set 改 remove 后原位 insertLine；`addPagedLine(index)` 用 `insertPage(index)` |
| `DecentPagedHologramLine.getPageIndex` | 返回"所在 DH 页在全息图的页号"而非"行在本分页行页列表的索引"，`removePage(line)` 删错行 | 改返回 `page.getLines().indexOf(line)` |
| `DecentHologram.clearLines` | 移除全部页（含第 0 页），此后 `getPage(0)` 为 null，所有取行方法 NPE | 原地清空第 0 页并删多余页，始终保留第 0 页 |
| `FancyHologramLine`(v2/v3) `getOffset`/`setOffset` | 直接返回/保存活动 JOML 向量，违反"返回副本"契约、造成别名 | `getOffset` 返回 `new Vector3f(...)`，`setOffset` 存副本 |
| `VaultUnlockedAccount` getBalance/deposit/withdraw | 接收 currency 却始终操作默认货币（canHold 对所有同源货币返回 true） | 世界级账户改用 Vault2 币种专用重载；全局账户因 API 无"无世界+币种"重载回退默认币种 |
| `VaultUnlockedChatServiceWrapper.getProfile` | `worldName` 为 null（最常见全局调用）时整条链坍缩为 empty，前缀等信息全空 | 补 `resolveProfile(player)` 回退，外层 flatMap 改 map（与 getGroup 一致） |
| `WrappedChatProfile` / `VaultUnlockedChatProfile` 信息节点 | `booleanInfoNode` 等用 `Optional.of(Vault 默认值)`，缺失键也返回 present，违反"缺失即 empty"契约 | 删除三个覆盖，改用经正确 getInfoNode 路由的默认实现 |
| `GroupManagerPermissionHolder.inGroup` | 仅查主组继承树，忽略 `addSubGroup` 加入的子组（与 Vault 层 playerInGroup 不一致） | 补查用户子组及其继承 |
| `GroupManagerChatProfile.getName` | `Optional.of(user.getLastName())`，无 lastName 时 NPE | 改 `Optional.ofNullable` |
| `LuckPermsChatProfile.setDisplayName` | 建 DisplayNameNode 未带 `options().context()`，世界级档案设的是全局、清的是世界上下文 | 补 `options().context()` |
| `LuckPermsChatController.loadProfile(player, world)` | `loadUser(uuid)` 缺 username 提示，与非世界重载/组控制器不一致 | 传 `player.getName()` |
| `TestSuite.executeStep` | 普通 `test()` 步骤断言失败被 `assertionFailure` 与 `.exceptionally` 各记一次 FAIL | `.exceptionally` 跳过 RecordedAssertionError |

### 经核实后**有意不改**（属设计权衡/无可用 API，改动会破坏兼容或需人工决策）

| 项 | 原因 |
|---|---|
| `BankServiceWrapper.getBank(String)` 永不返回 empty | Vault1 `Economy` 无 `isBankName`；改用 `getBanks().contains()` 会给每次查询加 O(n) 且改变"惰性句柄"语义。 WrappedBank 句柄在操作时由 Vault 校验，属可接受设计 |
| `VaultUnlockedPermissionServiceWrapper` 组方法用缓存版 `getGroup` | 组通常已缓存（LuckPerms 启动即加载、GroupManager 直读）；改用 `resolveGroup().join()` 会把主线程阻塞面扩大（与下条权衡冲突） |
| wrapper/vault(unlocked) 权限/聊天 `.join()` 无超时 | 与经济包装器的 5s `tryResolve` 不一致；但权限路径加超时→超时返回 false 可能造成误判拒绝，风险高于有界阻塞。保留为既有设计 |
| `FancyHologram` v3 `persist()` 空实现 | v3 公共 API（`FancyHolograms.get()` → factory/registry/controller/plugin）未暴露 save 方法，无可用 API 可接；v3 疑为自动持久化 |
| `DecentHologram` 取行器不一致（getLines/iterator 跨全部页 vs getLineCount/getLine 仅第 0 页） | 属既有设计取舍，统一需重定义索引语义，影响面大 |
| GroupManager `getGroup`(全局) vs `loadGroup`(默认世界) 命名空间、Vault `playerHas`(玩家所在世界) vs `playerAdd/Remove`(默认世界) | GM↔Vault 的世界映射存在真实歧义，任一方向都会改变部分部署的行为；需人工决策后再改 |

## 7. 不可信客户端输入审计（"不得信任任何用户输入"）

针对"客户端可改代码控制输入"的威胁模型，逐一审计了客户端输入可达 ServiceIO 的路径：

| 输入面 | 结论 |
|---|---|
| `/service`（info/convert/test）命令 | 全部 `service.*` 权限门禁、默认仅 OP；参数经 `ControllerArgumentType` 精确名匹配（不匹配抛 IllegalArgumentException 由 Brigadier 拦截），convert 用 AtomicBoolean 防并发、并禁止 source==target。普通玩家无权触发任何写操作。 |
| 占位符参数（world/uuid/currency，可能经聊天类插件被客户端注入） | 全部只读；`PlaceholderStore.resolve` 整体 try/catch→返回 null（不崩）；UUID 解析用 `throwing(IllegalArgumentException)` 包裹→坏输入返回 null；world 查询 null 校验。`account_<uuid>` 查他人余额属 IDOR，但与上游 VaultUnlocked 占位符行为一致（PAPI 模型固有）。 |
| 经济金额（deposit/withdraw/setBalance） | 客户端可经商店插件传入 NaN/Infinity（`Double.parseDouble("NaN")`），曾导致 `new BigDecimal("NaN")` 崩溃或 NaN 入库。**已加 isFinite 校验，非有限金额返回 FAILURE**（见提交 2c1d985）。 |
| 数字解析（parseInt/parseDouble/UUID.fromString/new BigDecimal） | 全量扫描：UUID 占位符处已容纳；其余均解析后端存储值（非客户端串）；MetadataHolder 的解析按契约抛 NumberFormatException（内部数据）。 |
| 测试套件 | 仅操作执行者自身账户（`createAccount(player)`）并末尾 `deleteAccount` 清理，不波及他人。 |

高负载稳定性备注（非逻辑 bug，属固有设计）：`WrappedBank.getOwner/getMembers`、`getAccounts` 等遍历 `getOfflinePlayers()`（O(n) 磁盘读取），高频调用可能造成延迟——这是 Vault 1.x 银行/所有者 API 的固有限制；同步桥接（`.join()` / 5s `tryResolve`）在主线程阻塞是 Vault 同步 API 的固有约束。

## 后续若要"前进一步"的注意点

- 如果日后想在 1.21.11 上用 FancyNpcs / DecentHolograms 的 provider，**服务器里也要装对应的 1.21.x 版本**
  （FancyNpcs 2.9.x、DecentHolograms 2.9.x），而非 2.10+/2.11。
- 不要随手把 provider 依赖或 toolchain 升到 25+，否则 JDK 21 下会立即编译失败。
- 若合并上游更新，重点检查三处会漂移的地方：`build.gradle.kts` 的 `paper-api` 与 `toolchainJvm`、
  `module-info.java` 的 adventure 模块名、以及各 provider 的依赖版本。
